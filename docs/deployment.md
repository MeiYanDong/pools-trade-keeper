# Cloud deployment runbook

Target supplied by the user:

```text
SWAS instance id: 061a4d28fb5a43bbabf92da7583e0cbe
public IP: 47.251.28.201
```

The first cloud unit is Shadow-only. Do not open a public dashboard port; outbound RPC plus SSH is sufficient.

## Required order

1. Verify the SWAS instance, region and endpoint from the control plane.
2. From a clean checkout using `.node-version`, run `npm ci && npm run verify`. For a manual release, run `deploy/package-release.sh "$(mktemp -d)"`; the packager fails if macOS AppleDouble metadata is present. Deploy only the CI or manual artifact whose `dist/release-manifest.json` was generated by that verified run.
3. Create a dedicated `pools-keeper` OS user and `/opt/pools-trade-keeper`.
4. Put RPC credentials in `/etc/pools-trade-keeper/keeper.env` with mode `0600`; never copy them into the repository or unit file.
5. Install `deploy/pools-trade-shadow.service`; use the compiled `dist` runtime and production-only dependencies.
6. Complete a gap-free inventory backfill before starting the service.
7. Read back systemd status and recent evidence; success means Shadow observations only.
8. Install `deploy/pools-trade-shadow-runtime.conf` as the systemd drop-in `/etc/systemd/system/pools-trade-shadow.service.d/10-runtime.conf`, then daemon-reload and start the service.
9. As root, run `NODE_BIN=/opt/pools-trade-runtime/node-v22.23.2/bin/node bash /opt/pools-trade-keeper/deploy/verify-shadow.sh`. The verifier also proves that systemd uses this exact runtime. A failed artifact hash, Node mismatch, stale/error evidence, restart, or disk usage above 89% blocks the release.

The host currently enforces the persistent journal budget in `deploy/journald-disk-budget.conf`. Installing that file is a host-wide operations change: record the before/after journal and filesystem usage in the deployment receipt, and do not delete application releases or evidence to satisfy the disk gate.

Wallet material is not needed for Shadow. A canary wallet must be initialized by the user on the target host or provisioned through an approved secret channel. Never paste a private key into SSH commands, service files, chat or logs.

## Artifact boundary

The deterministic manifest covers `dist/src`, package metadata and lockfile, the manifest generator, the systemd unit, the post-deploy verifier, the sniper specification, and the capability manifest. Verify it before switching a service to the new files:

```bash
node scripts/write-release-manifest.mjs --check
```

CI packages the verified files but does not deploy them. Deployment remains a manual external action until a reviewed secret channel, versioned release directory, health check, and rollback automation exist.

## Rollback and evidence preservation

Before a manual release, archive the current application directory as a versioned, read-only release and record its manifest hash. Never replace `/var/lib/pools-trade-keeper` or `/etc/pools-trade-keeper/keeper.env` during an application rollback.

If post-deploy verification fails:

1. stop the new unit without deleting its journal or evidence;
2. point `/opt/pools-trade-keeper` back to the last artifact whose manifest and post-deploy result passed;
3. reload systemd only if the unit changed, then restart the Shadow service;
4. rerun `deploy/verify-shadow.sh` and retain both failed and recovered outputs in the deployment receipt;
5. if the failure is disk pressure, do not delete evidence ad hoc—expand storage or move an explicitly archived, checksummed segment under a reviewed retention policy.

Rollback restores observation only. It never authorizes a transaction.
